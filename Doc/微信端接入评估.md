# 微信端接入评估：小程序 or 小游戏

> 评估时间 2026-10-22。基于仓库当前形态（Client 27M / App 5136 行 / 服务端自造撮合）。
> 结论先行：**主产品走小程序；如果要「游戏身份」和游戏中心的流量，另开一个小游戏做衍生玩法，不要把主产品整体搬进小游戏。**

## 一、现状盘点

| 项 | 现状 | 对迁移的含义 |
|---|---|---|
| 主客户端 | `Client/` 27M，其中 `img/` 26M，单张 mascot 最大 2.0M | 两边都要重做资源管线，小游戏首包 4M 更痛 |
| 前端体积 | `app.js` 7613 行 / 333K，`style.css` 116K，`index.html` 45K | 纯代码 ~500K，体量健康 |
| 渲染方式 | 主体 DOM（盘口五档、持仓表、聊天、公告横幅）；canvas 仅 4 处（股东历史、空头折线、分享图） | **95% 是 DOM → 迁小游戏等于重写，不是移植** |
| 推送 | 强依赖 SSE `/api/events`，全量快照 + `src/sseback.js` 背压 | 小程序/小游戏都无 `EventSource`，两边都要改 |
| 移动版 | `App/` 5136 行，已拆 7 个视图（login/market/stock/trade/rank/news/me）+ `api.js` 独立封装 | **天然的小程序页面栈基座** |
| 行情来源 | 自有服务端撮合引擎 + NPC 生成的模拟行情，不接交易所数据源 | 合规上的最大优势，见 §3 |

## 二、三条硬约束

### 1. 渲染模型（决定工作量）

小游戏只有一个全屏 canvas，没有 DOM、没有文本流、没有滚动容器、没有输入框。而本项目首屏就是：
盘口五档（3 帧一变）→ 持仓表 → K 线 → 弹幕聊天 → 公告横幅。

- 表格类密集文本在 canvas 里要做虚拟列表 + 文本裁剪 + 脏矩形，改造量远大于收益；
- 数字高频更新时，DOM 改文本节点的开销比 canvas 重绘整块更低；
- 输入、滚动、长列表、表情面板全部要自己实现。

**结论：小游戏不是「换个壳」，是把 UI 层从零重做一遍，且做出来更差。**

### 2. 推送协议（两边一样，不构成选型依据）

| | 小程序 | 小游戏 |
|---|---|---|
| EventSource | 不支持 | 不支持 |
| 可行替代 | `wx.request({ enableChunked: true })` 手动切帧 | 同左 |

都能复用 `sseback.js` 的背压思路：读不动就跳帧（每帧是全量快照，跳帧无损）。小程序还多了 `onHide/onShow` 生命周期，比 App 熄屏更好管——正好对着 10-22 那两次 OOM 的根因。

### 3. 身份与类目（真正的分水岭）

**「游戏」是一级类目，只属于小游戏账号。** 普通小程序账号选不了，也没法后期切换；两个 AppID 互相独立，注册即不可逆。

所以「把它当游戏做」在微信里的字面含义是：走小游戏账号，然后承担：

- 软著 + 游戏自审自查报告 + 工信部备案；
- 防沉迷、实名认证、适龄提示（强制，审核比普通小程序严得多）；
- 一旦有充值/内购，**必须网络游戏出版物号（版号）**，周期以月乃至年计。

## 三、题材风险（最容易被忽略，也最可能致命）

模拟炒股是个骑在两条红线上中间的位置：

| 风险 | 小程序 | 小游戏 |
|---|---|---|
| 证券类目 | 名称/内容含「证券、股票、交易」易被判需《经营证券期货业务许可证》 | 同左，且游戏审核更不看资质、直接拒 |
| 涉赌 | 一般无 | **高**：虚拟资金 + 涨跌 + 下注式操作，是游戏审核最敏感的组合 |
| 行情数据授权 | 不涉及（自造行情） | 不涉及（自造行情） |
| 投资建议 | 不荐股、不给买卖点即可 | 同左 |

两个关键判断：

1. **自造行情是本项目最大的合规优势**：不接交易所数据、不接真实交易通道、不荐股，就绕开了行情授权和证券牌照。这条必须在产品页明确写出来（虚拟资金、非真实市场、不构成投资建议）。
2. **金融题材 + 游戏类目 = 最危险的组合**。小游戏这条路上，你既是「游戏」又是「炒股」，等于同时接受两套最严的审核口径，而小游戏没有 web-view 可以退。

## 四、路线对比

| 路线 | 工作量 | 游戏分发流量 | 主要风险 | 判断 |
|---|---|---|---|---|
| A. 小程序 + web-view 套 `App/` H5 | 极小（域名备案 + 一个页面） | 无 | 企业主体、web-view 内体验有工具栏、拿不到订阅消息 | **当验证用，1 周内可上** |
| B. 小程序原生（或 uni-app）重写视图层 | 中（7 个 view 迁移 + 推送改造 + 资源压缩） | 无 | 类目归属要精心措辞 | **主线推荐** |
| C. 小游戏（Cocos/自绘 canvas）重做 | 大（UI 全部重画） | 有（游戏中心、好友榜、激励视频） | 版号（若内购）+ 金融题材涉赌判定 | 只适合做轻量衍生品 |
| D. 双轨：B 做主产品 + C 做衍生小游戏 | 中 + 小 | 有 | 账号需 openid 打通、共用行情服 | **最终形态建议** |

## 五、推荐路线

**「游戏感」和「游戏类目」是两件事，前者可以保留，后者要单独花代价去买。**

1. **主产品走小程序**：`App/` 已经是 7 个视图的移动优先结构，`view-*` → `pages/*`，`core.js`/`chart.js` 大部分可直接复用（小游戏/小程序的 canvas 2d 接口和 Web 几乎一致），只有 `api.js` 的 EventSource 要换。
2. **游戏化的部分留在小程序里做**：股娘养成、图鉴收集、盲盒、成就、赛季排行、每日签到、彩蛋（项目里已有 `彩蛋玩法方案.md`）。玩家不会觉得这不是游戏，你依然可以对外叫它游戏。唯一拿不到的是游戏中心的推荐位。
3. **如果一定要游戏身份**：另开一个小游戏账号，做 IP 衍生的轻量玩法（股娘养成 / 合成 / 放置 / 答题闯关），2D、包体可控、不含真实涨跌交易，用 openid 与主站账号打通、共用一个行情服。版号和审核风险被隔离在一个小体量产品里，主产品不受牵连。

## 六、第一步动作清单（按成本从低到高）

1. `img/` 26M 是硬伤：mascot 单张 2M 全部转 WebP（`Server/tools` 或 `art/` 里的脚本），Squoosh/cwebp 质量 82，预计能压到 3~4M。
2. `api.js` 的 `EventSource` 抽成可替换的 transport 层：浏览器走 SSE，小程序走 `enableChunked` 切帧，共用同一个帧解析器（`JSON.parse` + 尾包缓冲）。
3. 选 A 路线上一个体验版（域名备案 + web-view），先拿真实留存数据，再决定是否原生化。
4. 小程序类目措辞：定位「虚拟养成 / 模拟练习」，避免「证券、炒股、荐股、跟单」等词；股票名建议虚构化，不直接使用真实上市公司名。
