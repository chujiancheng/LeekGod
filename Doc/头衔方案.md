# 我是股神 · 修仙境界（头衔）方案

> 状态：**P0（MVP）已实现**（2026-10-20）。实现口径与本文的差异见 §15；P1/P2/P3 仍未实现。
> 相关文档：`彩蛋玩法方案.md`（§3.1 A 族发家线、§5 称号、§6 文案基调）、`券商方案.md`（门派 = 券商）、`项目知识.md`（§3.3 彩蛋的落地口径）。

## 0. 一句话

把「我账户里有多少钱」翻译成一句所有人都能秒懂的修仙黑话：**100 万是炼气二层，1000 万是结丹后期，1 亿是化神圆满，10 亿是合体真君**。境界不给你任何交易特权，它是你在**这服务器里的身份**——排行榜上、股东榜上、弹幕里，别人一眼就知道该不该跟你对盘。

---

## 1. 定位与边界

| 做 | 不做 |
|---|---|
| 把**收盘权益**映射成境界（服务端权威） | 新的交易机制（不碰撮合 / 定价 / 风控 / 券商参数） |
| 升境、跌境、历史最高境界 | 任何数值特权（费率 / 额度 / 券源 / 消息提前量 / 加钱上限） |
| 顶栏徽标、主页境界卡、规则面板整表 | 前端自己算境界（门槛数字一律吃服务端下发的表） |
| 复用彩蛋的 `seq` / `events` / 横幅通道 | 新增一套事件通道、新增 SSE 帧、新增 ack 协议 |
| 突破 / 跌境的演出与文案 | 盘中实时判定（会抖成刷屏，见 §4.2） |

**一句话纪律：境界是「观测层」的第二块屏幕。** 彩蛋回答"你刚刚做成了什么"（瞬时事件），境界回答"你现在是谁"（持续身份）。两者共用同一个权益口径、同一个收盘采样点、同一条事件队列。

## 2. 三条设计原则

### 2.1 门派管规矩，境界管面子

项目里已经有一个"身份系统"：**券商 = 出身门派**（`券商方案.md`），它给的是**规则特权**——费率、冷却、额度、券源、消息提前量、强平缓冲。境界绝不能重复这个位置，否则两套特权叠加会直接毁掉 `broker-probe.js` 好不容易调平的平衡。

所以分工写死：

| | 门派（券商） | 境界（修仙） |
|---|---|---|
| 决定 | 你**怎么打**（规则参数） | 你**是谁**（身份与排面） |
| 获得方式 | 开户时选、可转户、靠成交额升星 | 只能靠**权益**，转户不掉境 |
| 是否影响撮合 | 是（per-broker 覆盖值） | **永远否** |

两个维度正交：炼气期也能进钟信（大宗门），渡劫期也可能是天疯的客户（"化神大能，跑"）。

### 2.2 会跌的是境界，不跌的是名号

修仙小说里最有张力的桥段就是**跌境**。这里保留它：

- **境界**（当前身份）= 按**收盘权益**实时对应，会升也会跌；
- **名号 / 历史最高境界** = 只增不减，跌境后仍旧挂在主页卡上（"曾经是结丹真人"）。

这样跌境有戏剧性但没有惩罚性——不扣钱、不给 debuff、不封功能，只在收盘后播一条 L1 toast。**亏钱本身已经是惩罚了**，再叠一层系统惩罚就是劝退。

### 2.3 境界是收盘的，不是盘中的

盘中权益每个 tick 都在跳。如果徽标跟着跳，一个在 500 万门口横盘十分钟的玩家会看到「筑基圆满 ↔ 结丹初期」闪上百次，每一次都配一条播报——这不是爽感，是噪音。

所以：**判定只在收盘结算（与彩蛋同一个入口）**，盘中徽标只显示"已确认境界"；当盘中权益已经越过下一档门槛时，徽标加一层「突破中」的光晕（纯视觉，不判定）。突破动画与播报在收盘那一刻落地。

### 3.1 门槛为什么是这些数（四个锚点，不是随便凑的）

**锚点 ①：开户第一秒就有身份。** 炼气二层 = 100 万 = `account.initialCash`。新玩家一落地就是「炼气二层 · 持牌散修」，而不是"还没入门"。凡骨线压在 **90 万**（−10%），意味着**亏一个板才掉出修士行列**——起手不会立刻被打成凡骨。

**锚点 ②：低段密集，高段稀疏。** 100 万→225 万之间塞了 8 档（档距 8%~12%），一个正常交易日的 p90 振幅（实测日收益 p90 ≈ 8%）就够跨一档；1000 万以上档距拉到 25%~50%，跨一档要一段像样的行情。**前期高频正反馈、后期低频大成就**，这是修仙文的标准节奏，也是留存曲线需要的形状。

**锚点 ③：与 A 族彩蛋门槛对齐 9 处。** A 族 12 档是既有硬门槛，能少一套数字就少一套（详见 §3.2）。

**锚点 ④：1 亿 = 化神圆满 = 加钱终身上限。** `account.deposit.maxLifetime` 恰好 1 亿（当前已屏蔽）。这条对齐是刻意的：**化神之上，钱买不到**。哪怕将来重开加钱，纯靠充值最多把你送到化神圆满，再往上必须是交易赚的。这是这套系统最重要的一条"含金量声明"。

## 4. 判定口径

### 4.1 用哪个数

**只有一个**：`game.equityOf(acc)` 的 **r2 收盘值**——即 `Game.settleDay` → `Game.evaluateMilestones` 里那个 `equity`，与 `stateFor` 下发的 `account.equity` 逐位相等。

不引入第二套口径（不加 `deposited`、不看 `realizedPnL`、不看持仓市值单独排序）。理由和彩蛋 §2.1 完全一致：两边各算一遍必然差几毛钱，然后玩家投诉"我明明 1000 万了为什么还是结丹中期"。

### 4.2 升境

```
target = 最高满足 ladder[i].equity <= equity 的 i     // 二分，ladder 单调升序
if target > realmIdx:  realmIdx = target；播「破境」事件
```

- **一次可以连跳多档**（停机多日后补结算、或者一天翻倍）：直接落在 `target`，但**事件只播一条**，文案用最高那档（"一日之内，炼气七层 → 结丹初期"）。
- 已经越过门槛但当天没结算 → 不升。主页卡显示"已越过结丹门槛，等收盘结算确认"（复用彩蛋进度条同款文案）。

### 4.3 跌境

```
if realmIdx > 0 && equity < ladder[realmIdx].equity * (1 - demoteBuffer):   // buffer = 3%
    target = 最高满足 ladder[i].equity <= equity 的 i
    realmIdx = max(target, realmIdx - demoteMaxPerDay)   // 单日最多降 3 档
    播「跌境」事件
```

三个参数的作用，缺一不可：

| 参数 | 值 | 为什么 |
|---|---|---|
| `demoteBuffer` | **3%** | 没有缓冲的话，在门槛上横盘（499.8 万 ↔ 500.2 万）会天天跌境/升境来回播。3% 大约等于一个小波段的量级 |
| `demoteMaxPerDay` | **3 档** | 从结丹圆满（1300 万）一天崩到炼气（200 万）会跨 12 档，徽标一次性跳 12 级观感像 bug。限速之后是"一路跌境"的连续剧，反而更有戏 |
| 最低 0 档 | 凡骨 | 破产 = 凡骨。`equity < 0`（倒欠券商，B1-08）也是凡骨，主页卡额外标「道基已毁」 |

**跌境不触发任何机制后果**：不掉券商星级、不清自动化策略、不撤挂单、不给 debuff。

### 4.4 为什么不按指数折算

理论上"购买力"应该按大盘折算（指数涨 30%，同样 1000 万其实缩水了）。不这么做的理由：

1. **可解释性**：玩家能记住"一千万 = 结丹后期"。按指数折算是"一千万 × 昨收指数 / 基准指数"，没人算得清，也没人有感觉。
2. **和 A 族彩蛋同源**：A 族的 12 档全是名义金额，折算了就要维护两套尺子（彩蛋 §2.2 已经明确"两条尺子不要混"）。
3. **牛熊本身就是玩法**：牛市全员升境、熊市全员跌境，这是**特征不是 bug**——它让"境界"带上周期感，也正是修仙世界里"天地灵气枯竭，人人跌境"的隐喻。

代价是承认的：境界不能当"超额收益"的度量。所以 **P2 补一个副指标「道行」= 相对指数的超额收益**，只用于境界榜排序与主页小字，不影响境界本身。

### 4.5 状态与幂等（**与彩蛋最大的差异**）

| | 彩蛋 | 境界 |
|---|---|---|
| 幂等键 | `fired` 集合（同一 id 只触发一次） | **没有 `fired`** |
| 为什么 | 一辈子只该恭喜一次"第一次赚到 110 万" | 跌境后重新破境是**正常玩法**，同 id 必须能再次播 |

所以境界事件**只借 `seq`，不碰 `fired`**：每次升/降都 `seq++` 并塞进同一条 `events` 滚动队列（`kind: 'realm'`）。客户端沿用 `gushen_event_seq` 水位去重，不需要任何新协议。

需要新增的账户状态（挂在**已有**的 `milestones` JSON 里，零 schema 变更）：

```js
// Account.milestones 追加三个键（老档缺字段 = 默认值，自动兼容）
realmIdx: 2,        // 当前已确认境界档位（默认按当前权益推算，见下）
realmDay: 0,        // 上次变更的交易日号
realmSeq: 0,        // 最近一次境界事件的 seq（客户端用来判断"这条是不是境界"）
```

- **历史最高境界不新增字段**：直接用彩蛋已有的 `peakEquity`（单调不减的收盘峰值）反推 `idxOf(peakEquity)`。少一个字段就少一个会不一致的地方。
- 老档兼容：读到没有 `realmIdx` 的老档时，用当前权益 `idxOf(equity)` 初始化，**不播事件**（直接静默落位，同彩蛋 `initPeak` 的做法）。
- 为什么塞进 `milestones` JSON 而不是新列：项目对 schema 版本很保守（8→9 故意不写迁移、老档直接拒启）。境界 P0 完全是展示层，**不值得为它抬一次版本**。将来若要做"境界榜 / 全服境界分布"这类**按境界查询**的功能，再单独建表（`P1` 提到时一并升 schema 10，顺带把 `dao` 道号列一起加）。

## 5. 下发

### 5.1 服务端 → 客户端

`state.account.realm`（每帧，小对象）：

```js
realm: {
  idx: 16,                         // 当前档位（-1 = 凡骨）
  name: '结丹后期',
  short: '千万身家',
  honor: '金丹真人',
  group: 'jindan',                 // 大境界 key：配色 / 图标用
  equity: 10320000,                // 判定用的那个数（= account.equity，冗余但方便对账）
  peak: { idx: 17, name: '结丹圆满' },
  next: { idx: 17, name: '结丹圆满', equity: 13000000, need: 2680000, pct: 0.83 },
  pending: false,                  // 盘中已越门槛、等收盘确认
  dropping: false,                 // 当前处于跌境缓冲带（equity 在门槛 3% 以内）
  changedDay: 12,
}
```

`rules.realm`（**首屏 `/api/state` 带全表，SSE 增量帧只带 `{enabled:true}`**）：

```js
rules.realm = {
  enabled: true,
  groups: [ { key:'lianqi', name:'炼气期', honor:'炼气士', tone:'qing' }, ... ],
  ladder: [ { i:1, equity:900000, name:'炼气一层', short:'初入山门', group:'lianqi' }, ... ],
}
```

> 38 档全表约 2.5 KB。放进**每 tick 都重建**的 `rules` 里等于每秒发 3.5 KB 冗余数据——所以全表只走首屏，增量帧不带。客户端拿到后缓存在 `state.rules.realm.ladder`（`stateFor` 已按 token 返回完整对象，这条路径天然成立，不需要新接口）。

### 5.2 其他下发点（只加字段，不改语义）

| 位置 | 加什么 | 注意 |

## 9. 平衡红线（为什么一点特权都不给）

境界**零数值影响**，这是刻意设计，不是偷懒：

1. **不能给资金/额度**：`券商方案.md` §8 的校验清单里，"融资额度加成"是明令禁止项——境界按权益给额度，等于**赢家加杠杆更便宜**，会形成"钱生钱"的正反馈，把 `broker-probe.js` 调平的强弱关系全部推翻。
2. **不能给消息提前量**：会直接破坏 `消息分层方案.md` 的信息不对称结构——高境界玩家本就更赚钱，再给他们更早的消息，是双重优势。
3. **不能给费率折扣**：这会让"境界"变成"另一个券商"，两套 per-account 参数叠加，任何一次参数调整都要跑两倍回归。
4. **唯一允许的"奖励"是排面**：徽标、尊号、全服播报、境界榜、道号（P1）。**面子足够贵，因为它稀缺**——一个服务器只有几个人能挂「金丹真人」。

## 12. 守门测试清单（`test/realm.test.js`）

判定内核（纯函数，不 import market / npc）：

1. `idxOf` 边界：89.99 万 → 凡骨、90 万 → 一层、100 万 → 二层；每档门槛 ±1 分钱。
2. **开户即二层**：新账号首次结算权益 100 万 → `realmIdx === 2`，且**不播事件**。
3. 升境：1000 万 → 结丹后期（16）；1299.99 万 → 仍是 16；1300 万 → 17。
4. **连跳**：一天从 200 万到 1000 万 → 直接落 16，**只播 1 条**事件、文案取最高档。
5. 跌境缓冲：499.9 万（筑基圆满门槛 500 万，−0.02%）→ **不跌**；484 万（−3.2%）→ 跌到 400 万档（12）。
6. **单日降幅上限**：1300 万 → 100 万，一天只降到 10 档（13−3），次日继续降。
7. 凡骨：89 万 → `idx === 0`；−5 万 → 0 且 `mortal` 文案。
8. **反复破境不幂等**：跌到 13 再升回 16，事件照发、`seq` 递增（与 `fired` 无关）。
9. **历史最高不看回落**：峰值 1300 万、当前 200 万 → `peak.idx === 17`，主页卡仍显示「结丹圆满」。
10. **口径一致**：判定用的 equity 与 `stateFor().account.equity` 逐位相等（照抄 `milestones.test.js [8]` 的写法）。
11. **NPC 不判不落**：`persist.writeAccount` 对 NPC 写 `NULL`，`store.players()` 外零调用。
12. **老档兼容**：`milestones` JSON 里没有 `realmIdx` → 按当前权益静默落位、不播事件、不报错。
13. 收盘必标脏：境界变了的收盘要 `persist.touch(acc)`（没变也要，与 `peakEquity` 同理）。
14. 配置完整性：`ladder` 严格升序、`i` 连续、每个 `group` 在 `groups` 里存在、`startIdx` 存在、`ladder[i].egg` 指向真实彩蛋 id。

客户端（`client-day.test.js` 新增一节）：

15. 徽标文案吃 `account.realm.name`，**不从 equity 反算**。
16. 境界卡进度条宽度走 `style.width` 且夹在 0~1；`pending` / `dropping` 两种提示文案正确。
17. 规则面板 39 行全部来自 `rules.realm.ladder`（把服务端表改成假数据，UI 跟着变）。
18. 破境横幅与状态横幅不重叠（复用现有 `eggBannerTop` 断言的同一套几何桩）。
19. 老服务端没有 `account.realm` → 整卡隐藏、徽标不渲染、**不报错**。

## 13. 关键决策

**已拍板**：

| # | 决策 | 理由 |
|---|---|---|
| R1 | 纯展示层，**零数值特权** | §9；防两套 per-account 参数叠加 |
| R2 | 判定走收盘权益，与彩蛋同函数同取整 | 消除"我明明够 1000 万"的客诉 |
| R3 | 升/跌都只播事件、**不进 `fired`** | 跌境后重新破境是正常玩法 |
| R4 | 历史最高境界复用 `peakEquity` 反推，不新增字段 | 少一个会不一致的地方 |
| R5 | 状态塞进 `milestones` JSON，**不抬 schema** | P0 不值得为展示层升版 |
| R6 | 与 A 族 9 处门槛对齐 + 合并播报 | 同一天两条说同一件事的横幅很蠢 |
| R7 | 配色禁用 `--red` / `--green` | 这两个 token 是涨跌语义 |
| R8 | 境界不参与任何排序 | 沿用彩蛋 §8 红线 |

**待拍板**：

| # | 问题 | 选项 |
|---|---|---|
| R9 | 顶级要不要到 90 亿（≈31% 流通市值）？ | A：保持（传说感）；B：砍到合体圆满 15 亿收尾（可达性更好） |
| R10 | 跌境要不要播报？ | A：播（有戏）；B：只改徽标、不播（少打扰）——**推荐 A，但 P0 可先关，观察一周再开** |
| R11 | 道号（自定义 2~8 字）门槛 | A：结丹以上；B：元婴以上（更稀缺） |
| R12 | 是否需要「境界压制」类玩法梗（低境界在弹幕里被称"小友"） | P2 再议，P0 不做 |

## 15. P0 实现说明（与本文的偏差）

> 落地代码：`Server/src/realm.js`（判定内核）、`config.realm`（阶梯与文案）、`Client/app.js` 的 `renderRealmChip` / `renderEggCard` / `rulesRealmHtml`。权威口径已同步进 `Doc/项目知识.md` §3.6。

**按本文实现的**：38 档阶梯与四条锚点、收盘判定、3% 跌境缓冲 + 单日最多降 3 档、`realmIdx`/`realmDay` 塞进 `milestones` JSON（零 schema 变更）、境界事件不进 `fired`、`quietIds` 合并播报、`account.realm` / `rules.realm` / `players[].realm` 下发、顶栏徽标 + 主页卡 + 规则面板「境界」页、配色禁红绿。

**实现时新增/调整的**：

| # | 偏差 | 原因 |
|---|---|---|
| 1 | `realm.evaluateClose` **自己也会抬 `peakEquity`** | 彩蛋整体关掉（`config.milestones.enabled=false`）时 `milestones.evaluateClose` 不跑，`peakEquity` 会永远停在开户那一刻，「历史最高」退化成当前境界。同一个包络表达式两处写，不会打架 |
| 2 | 加了一条 **`realmDay` 同日守卫** | `settleDay` 的收盘段与夜间段都会走到判定；别指望两段之间价格永远冻结——判两次就可能把同一档破境播两遍 |
| 3 | `config.realm.text.up` **只给 14 个关键档位写了台词**，其余走通用模板 | 38 条台词维护成本高于收益；小阶突破本来就不该抢戏（一档一个横幅已经很密了） |
| 4 | 跌境到凡骨**可能跨好几天**（受单日 3 档限制），「道基已碎」会晚出现 | 这是设计意图（一路跌境的连续剧），不是 bug；文案里那个 `{equity}` 取的是**跌到 0 档当天**的权益 |
| 5 | 跌境文案在权益 < 10 万时**强制 gentle**（复用 `milestones.gentleBelowEquity`） | 与彩蛋同一条软着陆规则，不另立一套 |
| 6 | 股东榜的玩家行**也加了徽标** | 原计划排进 P1，实际成本只有一个 `store.get` + `brief`，顺手做了 |
| 7 | 排行榜的境界是**行内徽标**而不是独立列 | 列会挤压现有的「券商 + 组内名次 + 星级」那段宽度（窄屏已经贴边），行内小徽标不占列 |
| 8 | `view()` 额外下发 `total` / `changedDay` / `honor` / **`peakEquity`** | 前端要做「第 N / 38 档」与 hover 文案，少一次本地拼接就少一处口径分歧；`peakEquity` 是给主页卡用的，彩蛋关掉时 `events.peakEquity` 根本不下发，借它会退化成当前权益 |
| 9 | 倒欠券商（权益 < 0）时 **`mortalDebt` 优先于 gentle 软着陆** | 原方案是"亏到一成以下不嘲讽"，但负权益必然 < `gentleBelowEquity`，这条分支实际永远走不到，玩家会看到"本金还有机会重新长出来"——对倒欠的人是假话。文案改成先说欠了多少，且金额取绝对值（`fmtMoney(-5万)` 带负号，会读成"倒欠 -5 万"） |
| 10 | 规则页的 **3% / 3 档 / 1 亿改为读下发值** | 原实现把这三个数写在文案里，改了 `config.realm.demoteBuffer` 说明页就开始说谎。`ladderForClient()` 现在带 `demoteBuffer` / `demoteMaxPerDay` / `depositCap` / `depositCapTier`（lite 帧仍只带 `enabled`） |
| 11 | 彩蛋关掉时 **称号段 / 称号计数 / 回撤列整段不渲染** | 否则会显示「已获称号 0 个」「还没有称号」「回撤 0.0%」，把"这个功能没开"说成"你一次都没回撤"——0.0% 是假信息，不是空态 |
| 12 | 破境横幅的**左边线按大境界上色**（`realmGroup` + `--rtone`） | 否则「破境」只是一条按稀有度上色的普通横幅，和一次赚钱彩蛋长得一样。`.egg-banner.realm` 原本是个没有任何规则的死类名 |

**刻意没做（P1/P2）**：全服破境播报（L4，要等股神墙一起做）、道号自选（要抬 schema 10）、境界榜页面、弹幕境界前缀、`/open/v1/account` 的 `realm` 字段、跌境演出（掉色 / 裂纹）、「道行」超额收益副指标。

**验证**：`Server/test/realm.test.js` **107 条** + `Client/test/client-day.test.js` **712 条** + `npm test` 11 个文件全绿（exit 0）；HTTP 冒烟走临时库（`/api/state` 下发 38 档整表与 `account.realm`），正式服与 `data/game.db` 未碰。

**没验到的**：本会话的沙箱里 Chrome 起不来（`--headless --dump-dom` 也零输出），**新卡片与新徽标的真机视觉没截到图**。CSS 只做了静态审查 + 客户端对 `style.css` 的接线断言，上线前建议在浏览器里看一眼浅色三主题（护眼 / 晴蓝 / 樱色）的境界色对比度。

> **复查补记（同日）**：第一版有个典型硬伤——`app.js` 用 CSSOM 写了 `--rtone`，`style.css` 里却没有一条 `var(--rtone)`，于是"境界色"只在变量里存在，卡片永远是 `--ink`；而当时的 DOM 断言只验"变量已写入"，全绿。现在四处真正消费该变量（境界名 / 尊号 / 修为条 / 破境横幅），并**在测试里直接读 `style.css` 断言消费点存在**——DOM 桩测不出 CSS 有没有读变量。另外修正了凡骨文案的"60 万 元"（单位重复）、`mortalDebt` 死分支、规则页写死 3%/3 档/1 亿、彩蛋关闭态的三个假信息（见上表 9~12）。
